Snapping requires an exact match, a punctuation/case match, or a ≤2-character typo **that also shares its first word** — that last condition is what stops edit distance from ever merging two genuinely different modules. Unknown module names pass through untouched.
- **A module declared in the outline with no parts is reported and NOT created.** Goodman's `Electric Heater Assm` is subtotalled at $0.00 with no rows. An empty sub-assembly would read in every comparison as a module this product has.
- **`ImportBomPanel` defers its `onImported` refetch until the panel closes.** `ProductsPage` does `if (loading) return <LoadingList/>`, so refetching while the panel is open unmounts it mid-render and takes its results with it. Harmless when a single-product import navigated away on success; with a four-product workbook it destroys the only report of what was written, per-product links included.
- **A module can only be deleted while EMPTY, and the server enforces it (409).** The schema cascades SubAssembly -> Part -> Cost/Measurement, so deleting a populated module would silently take an arbitrary amount of captured teardown work with it on one click. The UI hides the control on a populated module rather than offering a guaranteed error. Do not add a `force` flag without a much stronger confirmation than a browser `confirm()`.
- **Duplicate module names on one product are refused even though the DB has no unique constraint.** Two sub-assemblies CAN legitimately share a name for imported data (see `subAssemblyRepository.findOrCreate`), but a human clicking Add Module twice has almost certainly double-submitted, and two identically-named modules split every per-module rollup in a way that reads as a data bug rather than a duplicate.
- **Authored parts write through `partRepository.normalise()`, the same allow-list the CEDARS importer and the seed use.** That is why a form field arriving as the string "8600" is coerced correctly, and why Photo IDs normalise to uppercase without the form knowing anything about it. Never add a second coercion path for authoring.
- **There is no in-app cost editor, so authored parts are UNCOSTED — deliberately, and visibly.** `partService.createPart` does not create a Cost row: a part with no cost record reads as "not costed yet" everywhere and is counted in the cost view's `uncostedPartLines`. Writing a row of zeros instead would assert the part is free, which is a different and false claim. If a cost editor is added, it belongs alongside Geometry / Part Information on the part row.
- **Verification scripts must not pass every product id to `compareProducts` / `buildBestOfBest`.** Both cap at five and THROW above it, so a script that hands over the whole database crashes instead of reporting — which is exactly what happened once the workbench made a sixth product trivial to create. `verify-seed` and `verify-bob` now resolve the seeded models by name and note anything extra.
- **The expanded part-detail table cell is WIDER than the visible card, and that is pre-existing.** Measured: the parts table is 567 px collapsed and 1457 px expanded, with the widest elements being the Geometry / Part Information `grid sm:grid-cols-2` blocks at 1191 px. `ui/table.jsx` wraps every table in `overflow-x-auto`, so it scrolls rather than breaking the page. **The consequence for anything new added to that cell: `w-full` does NOT mean "the card's width" there — 100% is the over-wide cell.** A child that needs to stay visible must cap against the viewport, e.g. PUI's `max-w-[min(32rem,calc(100vw-8rem))]`, and should be left-aligned rather than `mx-auto` (centring inside a 1191 px cell pushes content off a narrow viewport). Fixing the cell width itself would mean reworking the Geometry and Part Information layouts — a separate job, not a layout tweak.
- **PUI photos are keyed by PHOTO ID, not by part id — that IS the feature, not an implementation detail.** Photos are captured and grouped by the label on the physical part at teardown time, before anyone knows which BOM row they belong to; entering an existing ID on a part SURFACES photos it never uploaded. Two parts sharing an ID legitimately show the same set. `Part.photoId` is deliberately non-unique. Re-keying `puiStore` by part id would destroy the whole workflow.
- **The Photo ID is server-side (`Part.photoId`); the image bytes are browser-local.** That split is deliberate: the ID is BOM metadata that must survive a browser change, travel with the record and eventually let a shared photo store be queried; the bytes belong in SharePoint/Blob, which this build doesn't talk to. Don't "simplify" by moving the ID into IndexedDB too.
- **`lib/photoDb.js` owns the IndexedDB version and the upgrade for EVERY image store — never declare `DB_VERSION` in a store module again.** IndexedDB has one version per database. Two modules each with their own version means the one opening with the lower number fails with a `VersionError` — a browser-level break of a feature that previously worked, appearing only after the newer feature has been used once. To add a store: bump the version there by one and add another idempotent `if (!objectStoreNames.contains(...))` block.
- **Photo IDs are normalised to trimmed UPPERCASE in two places on purpose** — `partRepository.normalise()` server-side and `puiStore.normalisePhotoId()` client-side. They must agree, or a part saved as `"c1"` points at an empty photo set stored under `"C1"`. Duplicated rather than shared because frontend and backend are separate npm packages, same tradeoff `lib/api.js` notes for `PERSONAS`.
- **The PUI slot grid follows the SAVED photoId, never the input text.** Rendering photos for half-typed input would flicker through unrelated sets on the way to "CAB-001". The unsaved state is signposted instead.
- **A model-number match wins outright in `filterProducts` — don't "simplify" it into one substring sweep.** The FJ5ANXA18L's description literally names the FJ5ANXC48L ("one tier below the FJ5ANXC48L in the same FJ5ANX family"), so a plain description search for an exact model number returns two products. When the query appears in any product's `name`, only those are returned and the description sweep is skipped. A partial family code still matches both Carriers, which is what you want. `verify:search` pins this as a named regression.
- **Repository search, brand facet and selection live in the URL (`?q=`, `?brand=`, `?sel=`).** Selection especially: the tray exists to assemble a set and open it in Compare, and a user hitting Back would otherwise lose it. Typing uses `replace` so the Back button isn't polluted per keystroke. Selection ids are written back in **id order**, not click order, so the first id — which Compare and Best-of-Best both treat as the baseline — stays the lowest-id product instead of depending on which card was clicked first.
- **Superlative badges rank over the WHOLE repository, never the filtered subset.** Filtering to one brand and recomputing would crown that brand "Lowest cost in set", which is a confidently wrong badge of exactly the kind the Best-of-Best view is careful to avoid. Selection is likewise derived from all products, so a selected card hidden by a filter keeps its chip.
- **Selection chips show brand AND model, deliberately bypassing `makeProductLabeller`.** That labeller drops the model when a brand is unique — right for chart legends, wrong for a tray where the user picked one specific unit and a chip reading "Goodman" doesn't confirm which. Two different jobs; don't unify them.
- **`asChild={condition}` on a `Button` is a trap.** asChild needs exactly one child element, so a conditional forces the non-link branch to wrap its icon and label in a wrapper element — which becomes the button's only flex item and makes the icon overlap the text. Render two separate `<Button>`s per branch with children directly instead. This shipped broken once and was caught by looking at a screenshot, not by a text assertion.
- **`askService` REFUSES rather than guesses, and that is the feature.** An unmatched question returns `understood: false` with suggestions and no figures — never a nearest-match answer. A wrong-but-confident answer about a competitor's cost gets acted on; "I don't handle that" gets rephrased. Don't add a fuzzy fallback that always produces something. For the same reason, an ambiguous brand (Carrier has two models) **widens** — comparisons include both, two-sided questions answer every pairing — and says so in `notes`; never silently pick one.
- **`askService` is NOT a stub, unlike `aiService` next door.** Every figure comes from `benchmarkService` against live data; only the *language* layer is rule-based. When Azure OpenAI lands it should replace `parse()` alone — the answer builders are just queries and stay as they are. Don't let anyone "replace the stub" by rewriting the whole file.
- **Ordering inside `askService.parse()` is load-bearing.** `best of best` must be tested before any other "best" (or "Show me the Best-of-Best summary" reads as a module question); `executive` before generic summary handling; `difference` before `compare` (the difference phrasing contains no "compare"); module questions before superlatives (there is no bare "best" superlative to fall back on). Each is commented in place — add new intents with the same care.
- **The Ask page's example questions come from the backend (`GET /api/ai/ask/examples`).** They're exported from the same module that parses them, so the UI can't advertise a question shape the parser doesn't handle. Don't hardcode them in the component. Fallbacks in the page apply only on request *failure* — never during the loading gap, or the list visibly changes length under the user.
- **Never bundle a real manufacturer logo into the repository catalog.** `ProductCatalogEntry` shows a brand **monogram tile**, not the Goodman/Carrier/Trane/Bosch marks. Two reasons and both stand on their own: those are registered trademarks this repo has no licence to redistribute, and a real logo sitting beside fabricated cost figures is precisely the combination that turns an illustrative screenshot into apparent published competitive intelligence. The same logic applies to product photography — the image is a drawn placeholder, and `ProductsPage` says so once above the list. Swap in real imagery only alongside real teardown data.
- **The catalog's superlative badges are ORDERING, never arithmetic.** "Lowest cost in set" and friends are a min/max over figures `/reports/compare` already computed — the identical operation `/reports/best-of-best` performs on the identical values, which is what guarantees the badges and the leaderboard agree. Don't ever compute a total, share or delta in `ProductsPage`. And keep `computeSuperlatives`'s three refusals: nothing awarded below 2 products, above `MAX_COMPARE` (past the cap the trailing metrics chunk is a thinner executive payload, so the ranking would be over unequal data), or on a tie.
- **`ProductCatalogEntry` stays presentational — it fetches nothing.** Superlatives are computed once by the page and passed in, exactly as the metrics are. That's what makes it impossible for an entry to trigger its own request or to disagree with the page that rendered it, and it's the contract the card it replaced also kept.
- **`splitNotes` must always fall back to printing `notes` whole.** It peels the seed's `ILLUSTRATIVE DATA —` prefix off into a badge so the description reads as prose. If the seed's wording ever changes, the regex misses and the entire string renders unstyled — which is the correct failure. Never restructure this so a wording change can silently drop the disclaimer.
- **The global nav is three workflow sections, in order: How To Use → New Project → Competitive Intelligence Engine.** Don't add a fourth top-level item. Anything analytical belongs inside CIE (add a `CieSubNav` tab or a capability card on `/intelligence`); anything to do with getting data in belongs inside New Project. The whole point of the restructure was that four peer nav items made the app read as four tools.
- **Routes were deliberately NOT moved during the nav restructure.** `/`, `/compare`, `/best-of-best`, `/products/:id*` and `/workflow` all still resolve exactly as before — the sections are a grouping layer over them. That's what kept every bookmark, deep link and verification suite working through the change, and it's why no existing page needed editing. If a future pass really does want `/cie/*` paths, add redirects from the old ones rather than breaking them.
- **`CieSubNav` renders from `App.jsx`'s layout, not from inside each page**, and is suppressed on `/products/:id*` because those already carry `ProductSubNav`. Two stacked tab rows read as clutter rather than hierarchy. Adding the sub-nav to a page directly would also undo the "existing pages untouched" property above.
- **Build status vocabulary lives in `lib/buildStatus.js` — never re-declare it.** Live / Stubbed / Partial / Planned, their badge variants and the neutral icon treatment are shared by `WorkflowPage`, `HowToUsePage`, `NewProjectPage` and `IntelligencePage`. Four private copies would drift the first time something stubbed goes live. And keep the rule those pages follow: **anything labelled Live must have a working link**; if it doesn't work, it's Planned and gets no button.
- **Never label a product by brand alone in a comparison view — use `makeProductLabeller()` from `lib/format.js`.** The set contains two Carrier models (FJ5ANXA18L and FJ5ANXC48L). Brand-only labelling produced two identical "Carrier" rows, chart series and legend entries on the compare view, with no way to tell which unit was which. The labeller appends the model *only* where a brand appears more than once, so unique brands keep short labels and legends don't bloat. This class of bug is invisible until a second model from one brand arrives, so reach for the labeller in any new view rather than `row.brand`.
- **`seed.js`'s `CATALOG` order is the cost ramp, not brand grouping.** The two Carrier models are deliberately non-adjacent in the file — the A18L sits second, between the Goodman and the Bosch, because catalog order is seed order is the cost ramp that `productRepository.listProducts` relies on. Don't "tidy" the file by moving them together. Note the ramp only holds by *id* on a database seeded from empty: a product added later takes the next autoincrement id and sorts last regardless. Goodman keeps the lowest id, which is what the baseline convention actually needs.
- **The A18L is deliberately not the cheapest or lightest, despite being the smallest.** A 1.5-ton unit could plausibly have undercut the Goodman on cost and the Bosch on weight, which would have taken both documented crowns just by being small and rewritten the story this set exists to tell. It's positioned above both on content grounds (ECM + TXV + heat vs a PSC/fixed-orifice 4-ton; G90 steel vs composite). `verify-seed.mjs` asserts both the four crowns and the A18L's second-place positions, so a future numbers tweak can't quietly invert it.
- **The set is now at the five-product cap.** `compareProducts`, `buildBestOfBest`, `ComparePage` and `BestOfBestPage` all cap at five, and `ProductsPage.loadMetrics` chunks by five. A sixth product needs all of those raised together, or compare and best-of-best will start rejecting the full set.
- **Every product-vs-target comparison on the Best-of-Best view MUST use the like-for-like composite, never the raw one.** The raw composite spans every module seen on any product, including `Electric Heater Assm` which only 2 of the 4 carry — so it comes out *above* the cheapest real product's total ($286.27 vs the Goodman's $250.18) and reads as "the best-in-class target is worse than a unit you can buy". The like-for-like figures (`likeForLikeCompositeCost`, `headroomCost`) restrict the target to the modules each product actually has, which is the only fair comparison. `verify-bob.mjs` asserts BOTH that the raw composite exceeds the cheapest product AND that the like-for-like one doesn't, so a "simplification" back to raw totals fails the test rather than shipping quietly.
- **Cheapest-per-module and lightest-per-module are selected independently, and that's deliberate.** The composite cost target and the composite weight target are not the same bill of materials — a best-cost sourcing strategy and a best-mass one pick different modules. `sameSource` flags where they coincide. Don't collapse them into one "winner per module"; that would imply a single unit achieves both.
- **The Best-of-Best view ranks on `bySubAssembly` (module), not on `functionName`/`comparisonName`.** Those part-level columns are still consistent across all four products by design (see `seed.js`) and remain the right basis for a future *part*-level best-of-best — cheapest blower motor, lightest drain pan — but nothing reads them yet. If you build that, reuse the existing function/comparison vocabulary rather than inventing a parallel one, and note that `similarFlag: false` marks the five genuinely unique parts that have no cross-product counterpart.
- **`costPerKg` is a cost-efficiency metric, not a quality one, and the leaderboard says so on screen.** Lowest cost/kg wins (as specified), which means cheap heavy steel scores well and a light premium design scores badly by construction — the Bosch is simultaneously the lightest unit and the *worst* on cost/kg. The `note` field on that metric ships from the backend and is rendered under the cards; don't drop it, it's the difference between a useful number and a misleading one.
- **The CEDARS importer is verified against SYNTHETIC fixtures, not the real files — never claim otherwise.** The real Goodman/Trane/Carrier/Bosch exports are restricted customer files that cannot come onto this machine (PROGRESS.md's own dummy-data-only rule), so `CEDARS_BOM_Import_Spec.md` at the repo root is the *only* description of them available, and `frontend/scripts/make-cedars-fixture.mjs` reproduces that description as literally as it can. If a real import misbehaves in the sanctioned environment, **suspect the spec drifted from the files** rather than assuming the fixtures were wrong. The `.xlsx` fixtures are deliberately not committed (`backend/.gitignore`) — the generator is, so they're reproducible; and if a real file ever does land in `backend/fixtures/cedars/` it won't get committed by accident.
- **Import unit cost/weight are derived from the EXTENDED column (`Total Cost` / `Total Lbs`) divided by quantity, not read from the stated per-part column.** `benchmarkService` computes `extendedCost = unitCost × quantity`, so deriving the unit figure this way makes the app's rollups reproduce the source spreadsheet's own totals exactly — which is the one comparison anyone will actually run against an import. Taking the stated per-part column instead leaves every module total slightly adrift from the file. Where the two disagree the row is counted and surfaced in the UI, never silently reconciled. Don't "simplify" this back to reading `Cost Per part`.
- **`importService` must not strip `moduleName` off an imported row.** It's both the grouping key for building sub-assemblies AND a real `Part` column. The first pass destructured it away, which left every imported part's `moduleName` null while the sub-assembly tree looked completely correct — invisible on screen, only caught by reading a row back out of SQLite.
- **Nothing in the import path may build its own Part field list.** `partRepository.normalise()` is exported as `normalisePart` (and `costRepository.normalise` as `normaliseCost`) specifically so `productRepository.createTeardown()` reuses them. A second hand-written field list in the import path is how a new column ends up silently dropped on one code path but not the other.
- **`Part.geometryType` is validated in `partRepository.js` (`GEOMETRY_TYPES`), not the DB** — SQLite has no enum, same as `Measurement.type`/`Report.persona`. **`partRepository.js`'s `normalise()` is the allow-list for every Part column** — a new field added to the Prisma model needs a matching line in `normalise()` or it's silently dropped on insert (this bit the first pass at the BOM-template field expansion).
